# 文件描述层

Unix界面的一个很酷的方面是，Unix中的大多数资源都表示为文件，包括控制台、管道等设备，当然还有真实文件。文件描述符层是实现这种一致性的层。

Xv6为每个进程提供了自己的打开文件表或文件描述符

每个打开的文件都由一个struct file 表示,它是inode或管道的封装,加上一个IO偏移量

每次调用open都会创建一个新的打开文件;如果多个进程独立地打开同一个文件,不同的实例将具有不同的IO偏移量

另一方面，单个打开的文件（同一个struct file）可以多次出现在一个进程的文件表中，也可以出现在多个进程的文件表中。如果一个进程使用open打开文件，然后使用dup创建别名，或使用fork与子进程共享，就会发生这种情况。

引用计数跟踪对特立打开文件的引用数,可以打开文件进行读取或写入,也可以同时进行读取或写入
readable和writable字段可以跟踪此操作

系统中所有打开的文件都保存在全局文件表ftable中。文件表具有分配文件（filealloc）、创建重复引用（filedup）、释放引用（fileclose）以及读取和写入数据（fileread和filewrite）的函数。

前三个函数遵循现在熟悉的形式。Filealloc（kernel/file.c:30）扫描文件表以查找未引用的文件（f->ref == 0），并返回一个新的引用；filedup（kernel/file.c:48）增加引用计数；fileclose（kernel/file.c:60）将其递减。当文件的引用计数达到零时，fileclose会根据type释放底层管道或inode。

函数filestat、fileread和filewrite实现对文件的stat、read和write操作。Filestat（kernel/file.c:88）只允许在inode上操作并且调用了stati。Fileread和filewrite检查打开模式是否允许该操作，然后将调用传递给管道或inode的实现。如果文件表示inode，fileread和filewrite使用I/O偏移量作为操作的偏移量，然后将文件指针前进该偏移量（kernel/file.c:122-123）（kernel/file.c:153-154）。管道没有偏移的概念。回想一下，inode的函数要求调用方处理锁（kernel/file.c:94-96）（kernel/file.c:121-124）（kernel/file.c:163-166）。inode锁定有一个方便的副作用，即读取和写入偏移量以原子方式更新，因此，对同一文件的同时多次写入不能覆盖彼此的数据，尽管他们的写入最终可能是交错的。

这两段代码 `fileread` 和 `filewrite` 是 xv6 文件系统中**文件 I/O 的核心分发器**。

它们位于系统调用层（如 `sys_read`, `sys_write`）和底层具体实现（如 `readi`, `writei`）之间。它们的主要职责是**根据文件类型进行多路分发**，并统一管理**文件偏移量（`f->off`）**。

以下是这两段代码的详细解析：

### 🎯 核心架构：多路分发

Linux/Unix 的核心思想是“一切皆文件”。为了支持普通文件、管道（Pipe）和设备（Device，如控制台、磁盘），xv6 在 `struct file` 中定义了一个 `type` 字段。这两个函数通过 `switch` 风格的 `if-else` 逻辑，将请求分发给不同的处理模块：

1.  **FD_PIPE**：进程间通信管道。
2.  **FD_DEVICE**：字符设备（如串口控制台）。
3.  **FD_INODE**：磁盘上的普通文件。

---

### 🔍 `fileread`：读取数据

```c
int fileread(struct file *f, uint64 addr, int n)
```

#### 1. 权限检查
```c
if(f->readable == 0) return -1;
```
首先检查文件结构是否允许读取。

#### 2. 管道读取
```c
if(f->type == FD_PIPE){
  r = piperead(f->pipe, addr, n);
}
```
如果是管道，直接调用 `piperead`。注意这里**没有**更新 `f->off`，因为管道是字节流，没有“偏移量”的概念（读过的数据就消失了）。

#### 3. 设备读取
```c
else if(f->type == FD_DEVICE){
  // ... 检查设备号合法性 ...
  r = devsw[f->major].read(1, addr, n);
}
```
如果是设备文件，通过设备开关表 `devsw` 调用对应驱动程序的 `read` 函数。这里硬编码了 `1` (CONSOLE)，说明 xv6 的设备读写主要针对控制台。

#### 4. 普通文件读取 (Inode)
```c
else if(f->type == FD_INODE){
  ilock(f->ip);
  if((r = readi(f->ip, 1, addr, f->off, n)) > 0)
    f->off += r;
  iunlock(f->ip);
}
```
这是最复杂的路径：
1.  **加锁**：`ilock(f->ip)` 锁定对应的 inode，防止多线程/多进程同时修改文件元数据。
2.  **底层读取**：调用 `readi`，传入当前偏移量 `f->off`。
3.  **更新偏移量**：如果读取成功（`r > 0`），**更新 `f->off`**。这是实现“顺序读取”的关键。
4.  **解锁**。

---

### 🔍 `filewrite`：写入数据

`filewrite` 的逻辑与 `fileread` 类似，但在处理普通文件（`FD_INODE`）时有显著不同，主要是为了**事务处理**。

#### 1. 权限与类型分发
同样先检查 `writable`，然后根据 `type` 分发给 `pipewrite` 或设备驱动 `devsw`。

#### 2. 普通文件写入与事务切片
```c
else if(f->type == FD_INODE){
  // ...
  int max = ((MAXOPBLOCKS-1-1-2) / 2) * BSIZE; // 计算单次事务最大写入量
  int i = 0;
  while(i < n){
    int n1 = n - i;
    if(n1 > max) n1 = max; // 切分写入块

    begin_op(); // 开启事务
    ilock(f->ip);
    if ((r = writei(f->ip, 1, addr + i, f->off, n1)) > 0)
      f->off += r; // 更新偏移量
    iunlock(f->ip);
    end_op(); // 提交事务

    if(r != n1) break; // 写入失败或磁盘满
    i += r;
  }
  ret = (i == n ? n : -1);
}
```

**为什么要用 `while` 循环切片写入？**
xv6 使用日志（Log）来保证文件系统崩溃一致性。日志的大小是有限的（`LOGSIZE`）。
如果用户试图一次性写入 1MB 数据，这可能会超过日志的容量，导致事务无法提交。
因此，`filewrite` 计算了一个 `max` 值（通常是几 KB），将大的写入请求**切分成多个小块**，每一块都在一个独立的事务（`begin_op` ... `end_op`）中完成。

**关键点：**
*   **原子性**：每次循环都包裹在 `begin_op()` 和 `end_op()` 之间。
*   **偏移量推进**：每写完一小块，`f->off` 就增加，确保下一次循环写入到正确的位置。

---

### 💡 总结：`f->off` 的重要性

这两个函数最重要的共同点是**维护 `f->off`**。

*   **`f->off` 属于 `struct file`**：正如我们之前讨论的 `fork` 共享文件描述符，父子进程共享同一个 `struct file`。
*   **并发影响**：
    *   当父进程调用 `fileread` 读取了 10 字节，`f->off` 增加了 10。
    *   如果子进程紧接着调用 `fileread`，它会看到更新后的 `f->off`，从而接着父进程的地方继续读。
    *   这就是为什么 `fork` 后父子进程读写同一文件**不会覆盖**，而是**衔接**的原因——因为 `fileread`/`filewrite` 修改的是共享的 `f->off`。
*   

这行代码是在计算**一次文件系统事务（Transaction）中，能够安全写入数据的最大字节数**。

它的核心目的是为了防止写入的数据量过大，导致所需的磁盘块数量超过了日志系统（Log）的容量限制（`MAXOPBLOCKS`）。

### 🧮 计算公式拆解

公式的核心逻辑是：**先算出能用来写数据的块数，再乘以块大小**。

```c
((MAXOPBLOCKS - 1 - 1 - 2) / 2) * BSIZE
```

我们可以把它拆解为以下几个部分：

#### 1. `MAXOPBLOCKS`：总预算
这是 xv6 日志系统允许一个事务修改的最大磁盘块数量（通常定义为 10）。这是我们的“总预算”。

#### 2. `- 1 - 1 - 2`：扣除元数据开销
为了写入数据，我们不仅需要数据块，还需要修改文件系统的元数据。这里减去的是最坏情况下的元数据块消耗：

*   **`- 1` (Inode 块)**：
    写入数据会改变文件大小（`size`）和修改时间，因此必须更新文件的 **Inode** 块。
*   **`- 1` (间接块)**：
    如果文件较大，可能需要分配或更新一个 **间接块** 来存储数据块的指针。
*   **`- 2` (空闲位图块)**：
    这是最保守的估计。为了分配新的数据块，需要修改空闲位图。在 xv6 中，位图可能跨越两个块（或者为了处理位图边界情况），因此预留了 **2 个块** 用于更新空闲位图（Bitmap）。

**剩余预算**：`MAXOPBLOCKS - 4`。这就是剩下的可以用来存数据的块数。

#### 3. `/ 2`：安全冗余
这是代码中最令人困惑的部分。既然剩下了数据块预算，为什么还要除以 2？

*   **原因**：**写前日志机制**。
    xv6 的日志系统要求，在数据真正写入文件系统的数据区之前，必须先写入日志区。
    虽然 xv6 的实现中，日志块和文件系统块通常是一一对应的，但这里的 `/ 2` 是一种**极度保守的安全策略**（或者是旧版本代码的遗留逻辑）。
    它假设最坏的情况：每写入 1 个数据块，可能需要在日志中占用额外的空间，或者为了防止计算误差导致溢出，强制将可用块数减半。
    *注：在很多 xv6 的变种或解释中，这个 `/ 2` 有时被认为是多余的，但在标准 xv6 代码中，它确保了即使加上各种边界情况，事务也绝对不会超过 `MAXOPBLOCKS`。*

#### 4. `* BSIZE`：转换为字节
最后，将计算出的“数据块数量”乘以块大小（`BSIZE`，通常为 512 字节），得到最终的字节数 `max`。

---

### 💡 举例计算

假设 `MAXOPBLOCKS = 10`，`BSIZE = 512`：

1.  **总预算**：10 个块。
2.  **扣除元数据**：10 - 1 (Inode) - 1 (间接块) - 2 (位图) = **6 个块**。
3.  **安全减半**：6 / 2 = **3 个块**。
4.  **最终字节数**：3 * 512 = **1536 字节**。

**结论**：在这个配置下，`filewrite` 每次循环最多只能写入 1536 字节。如果用户想写 4096 字节，`while` 循环会执行 3 次（1536 + 1536 + 928），每次都开启一个新的事务。

### 📌 总结
这行代码体现了系统编程中的**“防御性编程”**思想。它不追求单次写入的最大性能，而是优先保证**事务的原子性**和**日志系统的安全性**，防止因写入数据过多导致日志溢出，从而破坏文件系统的一致性。
